# Triage: what to fix first, across the twelve projects

Written 2026-11-20, after the comment sweep filed 577 issues from 959 tagged comments, and
after the test-execution audit of 2026-11-19 (see `test-execution-audit-2026-11-19.md`).

Most of those 577 are design questions — worth having, not urgent. This list is the subset
where the code is **doing something wrong now**, ranked. The ordering principle:

1. **Shipped code that returns a wrong answer silently.** Nothing else outranks this: the user
   gets a number, and it is the wrong number, with no error and no warning.
2. **Verification that is not happening.** Tests that do not run, laws not checked, suites
   commented out. These do not break anything by themselves; they are why the first category
   can persist unnoticed.
3. **Reachable crashes.** Worse than wrong answers for the caller's temper, better for their
   data.
4. **Records that mislead the next reader** — comments citing closed issues, placeholder issue
   numbers, test names that cite stale line numbers.
5. **Structural duplication.** Real, but it is a refactor, and refactoring under the first two
   categories is how defects get re-introduced.

## A note on the ordering

Tier 1 item 2 and Tier 5 item 21 are the same discovery seen twice. The duplicated `mill`
package is a structural problem; that the *same suspected defect* sits in both copies is a
Tier 1 problem. Fix the defect in both places first and leave the deduplication for its own
day — doing it the other way round means refactoring code you know to be wrong.

Tier 2 is ranked below Tier 1 but is what makes Tier 1 possible. Four of the twelve projects
have test directories that have never run, two of which no longer compile. Nothing in those
trees can tell you anything until they run again.

## Corrections to this list

**Number [#231](https://github.com/rchillyard/Number/issues/231) was ranked Tier 1, item 2, and
should not have been.** It was put there on the strength of its summary — *"`Representation.scala:1650`
returns `false` and `:1663` returns `None`, both under `TODO figure this out`"* — read as a method
returning a constant that a caller cannot tell from a real answer.

Investigation on 2026-11-21 showed otherwise. The two methods are `AnyRoot.canMultiply` and
`AnyRoot.convert`, and `false`/`None` are the conservative answers — "I cannot do this" — not
lies. `canMultiply`'s only caller is `representationsMatch`, which its own comment notes is used
only by `ExpressionMatchersSpec`, so it reaches no production code. `convert` returning `None`
lands in `Number.toPureNumber`, which falls back to `scale(PureNumber)`; the `Representation.add`
call sites are guarded to `Scalar`, which `AnyRoot` is not.

So the cost is lost exactness for rational-power roots, not a wrong answer — and addressing it
means implementing rational-root conversion and multiplication, which is a feature requiring a
decision about when such a conversion is exact, not a defect repair.

**The lesson for the rest of the list:** a tag that *sounds* like a wrong answer may be a
conservative decline. The question to settle first is what a caller does with the value, and the
answer is in the call sites, not the comment. The same investigation is worth doing before
starting any item here.

## Also found, not from this list

Number [#601](https://github.com/rchillyard/Number/issues/601) — `Rational.createExact` threw a
`NumberFormatException` for a non-finite `Double`, from outside its own `Try` block, so a method
promising `Try[Rational]` reported failure by throwing. It had no tagged comment and so appears
nowhere above; it surfaced from an intermittent CI failure whose seed turned out to be
reproducible. Fixed in PR #602.

Worth recording because it is the counter-example to this whole document: the sweep finds what
someone already noticed and wrote down. It does not find what nobody noticed.
